## 1. 验证目标与指标定义

| 目标 | 主张 | 指标 | 数据源 |
|---|---|---|---|
| a 经济性 | dedup+压缩上栈后账单不劣化、长会话更省 | 缓存命中率、等效账单（命中折价≈1/7）、prompt_tokens 增长率（tok/轮） | usage-ledger.jsonl + /api/status context_usage |
| b 记忆有效性 | 提炼的记忆高质量且注入后行为改善 | ①跨会话记忆问答命中率 ②提炼条目人工评审（相关性/准确性/无泄漏，3 档打分表） | 会话日志 + memory-extraction.json + 评审表 |
| c 压缩有效性 | 压缩保住关键信息、水位真降、不犯"忘记已压缩内容"的错 | ①压缩后锚点问答准确率 ②水位曲线在压缩点骤降可复现 ③视图语义正确（块摘要/标记消失） | /api/status compression 块 + /api/sessions/{id}/context + 问答断言 |

0a 基线（对照锚点）：命中率 91.4%、等效账单≈全价 21.7%、+1700 tok/轮（9 轮 31 步，小工作区）。

## 2. 对照架构（每个目标的 OFF 组是什么）

已核实的开关事实：
- 压缩：**CELESTEA_MEMORY_COMPRESSION=off**（runtime/src/compression-switch.ts:19）✓
- 记忆提炼：**CELESTEA_MEMORY_EXTRACTION=off**（runtime/src/memory-extraction.ts:144）✓
- dedup：**无 env 开关**（grep 全空）

因此 OFF 组设计分两类：

- **经济性（a）**：OFF 组 = **0a 历史基线**。0a 测的正是 dedup/压缩都不存在时的同通道表现，
  复刻其场景即天然对照。已知混淆变量：代码版本演进、模型漂移——报告中显式标注，结论按"粗证据"降级。
  （备选：若要干净对照，需给 dedup 加 env 开关或 git worktree 旧 sha——列为决策点 D1，默认走历史基线。）
- **记忆（b）/压缩（c）**：OFF 组 = kill-switch 现场对照（同代码、同脚本、同通道，仅 env 不同）。
  这是干净对照，差值可直接归因。

## 3. 场景设计（3 个）

### S1 · 短任务基线（10 轮）——目标 a
复刻 0a 的小工作区问答脚本。ON/OFF 在此场景无差异预期（10 轮不触发压缩），
价值在于**与 0a 基线对齐**、检验上栈后短任务无劣化。

### S2 · 长会话（35+ 轮）——目标 a + c
工作区代码问答与修改指令混合。**第 6–10 轮埋入 5 个"事实锚点"**（人为告知的约定/决定，
如"本项目默认端口定为 4321"——频道里别处不存在的信息）。持续对话直到压缩发生
（压缩由模型自主触发，指令给精确 0-based turn 区间——E2E 教训：turn id 从 0 起算）。
压缩发生后第 30+ 轮逐一提问锚点，计准确率。每轮记录水位，压缩点应见骤降。

### S3 · 跨会话记忆（2 会话 × 10 轮）——目标 b
会话 A：告知 5 条项目约定/偏好。会话 B（同工作区新会话）：提问只能由 A 的记忆回答的问题。
ON 组预期命中记忆注入；OFF 组（CELESTEA_MEMORY_EXTRACTION=off）预期答不出。
另对 A 的 memory-extraction.json 提炼条目做人工评审（3 档打分表）。

### 规模
每场景 × 配置 × 3 遍：S1=2 次运行（无 ON/OFF 之分则 3 遍即可）、S2=6、S3=6，共约 15 次运行、
**350+ 轮 LLM 调用**（放量规模，用户已裁决）。取中位数报告。

## 4. 执行基础设施（全部新写于 .probe/p3/）

- `drive.mjs`：驱动脚本——POST /api/sessions → /api/turn → 轮询 /api/status busy=false
  （复用 0b 驱动模式与 E2E 探针的 boot 经验：清壳环境 CELESTEA_* 泄漏、in-process 起服）。
- `collect.mjs`：每轮采集 usage-ledger 增量 + context_usage + compression 块状态，落 run JSON。
- `analyze.mjs`：汇总表——命中率/等效账单/增长率（a）、锚点准确率+水位曲线（c）、
  记忆命中率+评审表模板（b）。
- 每场景一个脚本化 prompt 序列文件（人工评审只发生在 b 的提炼质量环节）。

## 5. 判定标准（Go / No-Go）

| 目标 | Go | No-Go → 进调优 |
|---|---|---|
| a | S1 等效账单与 0a 基线持平（±10%）；S2-ON 等效账单 ≤ S2-OFF × 0.9 | 任一劣化超限 |
| b | S3-ON 记忆问答命中率 ≥ 4/5 且显著高于 OFF（预期 ≤ 1/5）；提炼评审 ≥ 中档 | 命中率差距不显著或提炼质量低档 |
| c | S2 压缩后锚点准确率 ≥ 4/5；每次运行在压缩点水位骤降可复现 | 准确率 < 4/5 或水位不降 |

## 6. 调优手册（测试只是输入，调优才是目的）

### 6.0 P3.0 必做的前置改动：常量可配化

nudge 水位与 preflight 阈值目前是**硬编码常量**（core/src/compression.ts:151/:161）。
参数扫描要求每次运行用不同阈值，改代码重编译不可行——P3.0 先把它们改成 env 可配
（如 `CELESTEA_COMPRESSION_NUDGE` / `CELESTEA_COMPRESSION_PREFLIGHT`，缺省回落现值），
drive 脚本按运行注入。这本身就是第一个"修改建议"，验证开工前落地。

### 6.1 参数寻优（sweep——不是 pass/fail，是找最优点）

- **网格**：S2 场景扫 nudge {0.4, 0.5, 0.6} × preflight {0.7, 0.8, 0.9} 粗网格，
  每格 2 遍。目标函数 = 等效账单最小，约束 = 锚点准确率 ≥ 4/5。
- **产出是 Pareto 前沿**（成本×保真度的权衡曲线），不是单点答案；最终取值由用户在前沿上拍板。
- 成本控制：全网格 9 格 × 2 遍 = 18 次运行太贵 → 先扫 3×2 粗网格找梯度方向，有梯度再细化。
  这正好回答 handoff 挂着的"nudge/preflight 用数据裁决"。

### 6.2 故障诊断树（症状 → 假设 → 修改建议 → 验证范围）

**目标 a 经济性劣化时：**

| 症状 | 首要假设 | 修改建议 | 重跑 |
|---|---|---|---|
| 命中率掉、账单升 | 压缩触发太频繁，suffix 缓存反复失效 | nudge 调高（压得更冷）；哲学改为"更保守触发" | S2 |
| 命中率平、账单升 | 压缩摘要本身的 token 开销吃掉收益 | 摘要长度上限 + 措辞要求精炼（见 6.3-3） | S2 |
| S1 短任务也劣化 | 哲学/工具 schema 常驻开销变大 | 压缩哲学文案瘦身；核对 system prompt 增量 | S1 |

**目标 b 记忆不达标时：**

| 症状 | 首要假设 | 修改建议 | 重跑 |
|---|---|---|---|
| 提炼评审低档 | 提炼 prompt 质量 | 重写提炼指令（粒度/格式/去噪）；参考评审表低分样本归因 | S3 |
| 提炼好但 B 会话答不出 | 注入策略问题（时机/条数/排序） | 注入条数上限、相关性排序、注入位置（见 6.3-4） | S3 |
| OFF 组也能答出 | 场景泄漏（信息在工作区文件里也能找到） | 锚点改为纯口头约定，脚本审查泄漏路径 | S3 重设计 |

**目标 c 压缩不达标时：**

| 症状 | 首要假设 | 修改建议 | 重跑 |
|---|---|---|---|
| 锚点丢失 | 哲学没要求保事实；或块区间把锚点切碎 | 哲学加"事实/约定/决定必须保留"条款；校验区间对齐 | S2 |
| 模型不主动压缩 | 哲学太软 / nudge 触发太晚 | 措辞指令化（0.8 以上已有先例：措辞升级）；nudge 调低 | S2 |
| 摘要质量差（在但没用） | 模型摘要能力/长度限制 | 摘要结构模板化（决议/事实/TODO 三段式） | S2 |

### 6.3 预备修改清单（验证前就预见得到的候选改动，按优先级）

1. **阈值 env 可配化**（6.0，P3.0 必做）
2. **观测增强**：压缩摘要的 token 长度、每次压缩的"压前水位→压后水位"进 /api/status 的 compression 块——没有这对数，6.2 的 a 类诊断只能猜
3. **摘要长度/结构参数**：块 schema 加 max_summary_tokens 或哲学内嵌长度要求
4. **记忆注入策略参数**：条数上限、注入位置（system vs 尾部瞬时）
5. **D1**：dedup env 开关（若决定给经济性做干净对照）
6. **哲学措辞 A/B**：两套哲学文案（保守触发 vs 积极触发）作为 sweep 的第三维（可选，看 6.1 粗网格结果）

### 6.4 调优循环纪律

每轮迭代 = **一个改动 → 一个 sha → 受影响场景重跑 → 前后对比表**（同指标同场景并排）。
禁止一次改多个变量（归因会烂掉）。迭代直到：三个目标全部 Go，且 6.1 的 Pareto 前沿上选定工作点。
最终产出：选定参数值回写为代码默认值 + 一份"为什么是这个值"的裁决记录（进设计文档 §6 同款格式）。

## 8. 风险与备注

- **统计噪声**：3 遍中位数统计意义薄；结论存疑时加遍数而不是硬下结论。
- **模型自主性**：压缩时机由模型决定，S2 运行间压缩点会漂移——断言按"模型实际块"核对（E2E 已踩过）。
- **成本**：基础验证 350+ 轮 + §6.1 粗网格 sweep 约 12 次运行（240+ 轮）+ 调优迭代重跑；
  总量可能到 700+ 轮 flash 调用。放量规模已由用户裁决接受，但每轮调优迭代前应报一次累计消耗。
- **执行方式**：驱动脚本是确定性代码，可由子代理写（minimax 五连崩的教训：任务书要短、
  单文件、带防崩快照）；跑实验与分析我来编排。
- **决策点 D1**：dedup 是否补 env 开关做干净对照（默认否，走 0a 历史基线）。
