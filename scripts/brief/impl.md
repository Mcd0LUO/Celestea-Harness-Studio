## 常规条款 · 实现阶段（派工时按本文件拼进简报；任务特有部分由派工者写）

- **边界**：只动 `<写死的 glob>`；不要碰 `<不该动的>`。与别的在飞 writer **写范围互斥**。
- **跑** `pnpm check:fast`（9 道、只读、约 40s）并绿。**不要**跑全量 `pnpm check`（派工者收口时跑）。
- **变异负控制**：每条新断言把实现**改坏一次**确认**真红**；报告写「改坏成什么 / 哪条红了 /
  原始输出」。不许写「我觉得会红」。
- **UI 与行为改动要真机验证，而且探针必须打在功能的「主场景」上** —— 那个功能存在就是为了那一刻。
  只在静态或边缘场景取证**不算**。实测教训：某次交付 13 条真机断言全 PASS，而缺陷正在主场景里
  （「消息还在下面继续来」时点回到底部）。断言要有非零几何 + 可见性 + 截图路径；
  本机 headless 用法见 `scripts/a11y/` 既有探针。
- **铁律 11**：断言只守**后果**，不守机制。判据：「这条断言红的时候，是**产品坏了**，还是
  **我换了实现**？」不许钉 `position: fixed`、某个 px 常量、某个 class 名。jsdom 量不了 ⇒ 去真机量。
- **报告 ≤ 1 屏**，写在 `results/<工号>-<短名>.md`：改了哪些文件（含行号）/ 变异怎么红的 /
  真机证据（原始输出 + 截图路径）/ **刻意没做什么**。
- **纪律**：不 `commit` / `push` / `stash`；不跑 `pnpm install`；不改门禁脚本；
  **负结论只当下界**（「我没搜到」不是「不存在」）。
